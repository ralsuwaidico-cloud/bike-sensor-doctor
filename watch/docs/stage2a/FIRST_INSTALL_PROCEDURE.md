# Cyclift Watch — first hardware installation: exact procedure (PROPOSAL — NOT APPROVED, NOT EXECUTED)

Factory-preserving layout, Stage 1 proof of concept (no Bluetooth). Every write step below needs the owner's explicit approval of
this document. Run on the owner's PC (Python 3.12, esptool 4.8.1, T-U2T on COM4). Never `erase_flash`, never `--erase-all`, never
eFuse commands. All writes use `--flash_mode keep --flash_freq keep --flash_size keep` (esptool then changes nothing it was not told
to: with all three set to keep it returns the file unmodified — esptool 4.8.1 `cmds._update_image_flash_params`). Every write is
followed by `verify_flash` (device-side MD5 comparison, read-only). The exact command list is generated by
`tools/stage2a/install_check.py commands` and stored on the PC as `RECOVERY_AND_INSTALL_COMMANDS_NOT_RUN.txt`.

## Order is safety-critical (emulator evidence)
The factory bootloader with its original 4 MB setting **boot-loops** as soon as the partition table lists anything above 4 MB, even
while the factory app is still selected (C2x). Install order: program → bootloader patch → table → switch. Rollback order: switch →
table → bootloader.

## Phase 5 — post-install verification (read-only), covers the whole 8 MB
`read_flash 0x0 0x800000 after.bin`, then `install_check.py verify-after backup after.bin firmware.bin plan_pieces`:

| Region | Expected after install | Rule |
|---|---|---|
| 0x0000–0x0FFF | unchanged | byte-identical |
| 0x1000–0x1FFF, 0x5000–0x5FFF | planned bootloader sectors | equal to planned pieces |
| 0x2000–0x4FFF, 0x6000–0x7FFF | unchanged | byte-identical |
| 0x8000–0x8FFF | planned partition table | equal to planned piece |
| 0x9000–0xDFFF factory settings | changed only by the factory app's own boot counter (`osw-config`) during C1/C2 | any other namespace → FAIL |
| 0xE000–0xEFFF OTA record 0 | unchanged | byte-identical |
| 0xF000–0xFFFF OTA record 1 | planned (seq 2) | equal to planned piece |
| 0x10000–0x20FFFF factory app | unchanged | byte-identical |
| 0x210000–0x3FFFFF factory files | unchanged | byte-identical |
| 0x400000 … +firmware size | Cyclift firmware | equal to the approved file |
| rest of app1 … 0x6FFFFF | still erased | all 0xFF |
| 0x700000–0x7FFFFF Cyclift settings/files | written by Cyclift at run time | may differ |
Anything else differing → **UNEXPECTED → FAIL → stop, recovery R-B**. The verifier's own tests flag a change in the ROM gap,
bootloader middle, OTA record 0, factory app, factory files, unused app1 tail, the partition table, and any other factory
settings namespace (CI `test_install_check.py`).

## Why the LILYGO firmware shows default settings after the table change — and what it can and cannot overwrite
ESP-IDF finds the settings store by its **label** `nvs`. The new table gives that label to the new, empty Cyclift area at 0x700000
and renames the factory area to `nvs_fac` (same place, same bytes). So whenever the LILYGO firmware runs under the new table
(checkpoint C3, recovery R-A, or an automatic fallback) it opens the empty Cyclift area and starts with defaults.
* Its original settings (0x9000–0xDFFF) **cannot** be overwritten by it: it never looks for `nvs_fac`.
* **It will erase the Cyclift settings area.** The factory source (`osw_config.cpp`, confirmed by the string
  "Invalid config version detected -> starting fresh..." inside the installed binary) wipes the whole default `nvs` partition when it
  does not find its own config version there. Under the new table that is 0x700000–0x705FFF (Cyclift settings / future Bluetooth
  bonds) — harmless for Stage 1 (no Bluetooth, no stored settings) but must be designed for before Bluetooth pairing is added.
* Its file system (`spiffs`, 0x210000) is its own and unchanged; it never touches `littlefs` (Cyclift files) or app1. The installed
  firmware contains no OTA-update code path in its source, so it does not write app slots.
* Recovery R-B (original table back) gives it back its real settings exactly.

## Recovery levels — package validated OFFLINE only; physical recovery NOT yet tested
| Level | Writes (all with keep flags, each followed by verify_flash) | Offline validation on the real backup (owner's PC) |
|---|---|---|
| R-A back to the factory app | original 0xF000 | factory app selected ✔ |
| R-B factory first 4 MB | original 0xF000, then 0x8000, then 0x1000 + 0x5000 | first 4 MB byte-identical to backup ✔, factory table + selection ✔ |
| R-C complete | full 8 MB backup at 0x0, then `verify_flash 0x0 backup` | equals backup fingerprint ✔ |
| Crash loop (no automatic fallback) | R-A over USB (auto-reset; fallback: hold BOOT, tap RESET) | — |
Package check also confirmed: manifest hashes, every original piece equals the backup's sector, the post-install verifier accepts
a correct install and rejects a 1-bit change in the factory app. None of this proves the watch's flash will accept the writes — that
is only shown by a real, approved recovery.

Stop rules: any failed verify → stop, R-B for the phase, report. Any unexpected checkpoint → stop, R-B, report.
