# Cyclift — device-independent integration architecture (owner directive 8 Nov 2026, Phase 3)

Purpose: the iPhone app is the product; the BikeComputer, the Apple Watch and the Cyclift Watch (LILYGO) are devices
that speak to it through contracts. Changing an iPhone screen, a training algorithm or a plan rule never requires a
firmware change; a firmware change never requires an app change unless the **device-facing contract** changes, and then
it changes by version, never silently. This document names the pieces that already exist in the code, the rules they
follow and the tests that guard them. Nothing here resumes LILYGO firmware work.

## 1. One authoritative workout / session model (app side)

| Record | Type | Identity | Owner | File |
|---|---|---|---|---|
| Planned session | `Workout` | `Workout.id: UUID` (stable for the life of the plan entry; edits keep it, versions log it) | Phone planner | Models.swift, Planning.swift |
| Recorded ride | `RideRecord` | `RideRecord.id: UUID`; `sourceId` = `health:<uuid>` / `board:<boardId>:<rideId>` / local id | The recorder (phone, or board via import) | Models.swift |
| Strength session | `StrengthSession` | `id: UUID`; `workoutId` links it to the planned session; `healthUUID` for imports | Phone | Hybrid.swift |
| Exercise | `Exercise.id: String` (catalogue slug, e.g. `goblet-squat`; custom = UUID string) | stable across plan, templates, logs, devices | Phone catalogue | Strength.swift |
| Set | `SetEntry.id: UUID` inside `ExerciseEntry` | position-stable (devices address sets by index inside an exercise) | Phone | Strength.swift |
| Completion | `TrainingLedger` derives status from records — never a second flag | Phone | WorkoutState.swift |

Rules: one record per real event (`addRide` / `addStrength` dedupe by board id, Health UUID, local id and ±2 min window);
a device may **report** an event but never create a second record; devices address sessions by the phone's ids.

## 2. Versioned device message schemas

| Device | Contract | Version field | Compatibility rule | Spec | Contract tests |
|---|---|---|---|---|---|
| BikeComputer | Link v1.x: 8-byte header + tag/len/value fields | `INFO` ver major/minor + `caps` bitmask | unknown tags skipped, truncated messages rejected whole; a feature is used only when its `caps` bit is set (ride sync 0x40, Wi-Fi 0x80, profile 0x100, settings 0x200, diag 0x400, ride steps 0x800) | docs/LINK_V1_2_SPEC.md, firmware docs | BCLinkTests, LinkV12Tests, DiagTransferTests, RideStepsSyncTests (vectors copied from the firmware) |
| Cyclift Watch (LILYGO) | protocol v1: `[ver][type][seq][len][payload][crc16]` | byte 0 `ver`; a frame with another version is dropped and counted | absent values are explicit (0xFFFF / 0x7FFFFFFF), never zero; new fields are appended and older readers ignore the tail; events carry `(deviceId, seq)` | watch/docs/BLE_PROTOCOL.md, firmware payloads.hpp | CyWatchWireTests (vectors generated by the firmware encoder), CyWatchSessionTests |
| Apple Watch | WatchConnectivity dictionaries (`WatchMessage`) | key set versioned by build; unknown keys ignored | additive keys only | BikeComputerWatch/WatchMessage.swift | WatchMessage tests in the watch target |
| Apple Health | HealthKit types | Apple's | import by UUID; export once per ride (`healthExportUUID`) | ios/OWNERSHIP.md | RideHealthExport tests |

**Negotiation.** The app never assumes a capability: BikeComputer features are gated on `caps`; the LILYGO link drops
frames of another `ver`; both sides log the mismatch and the Connections screen shows "update required" instead of
guessing. An incompatible change gets a new version/cap bit and both encoders in the repo, with the old one kept until
the owner retires it — never a silent break.

## 3. Ownership of recording and Health writes

See ios/OWNERSHIP.md (one owner per value; the three competing-recorder cases). Summary: the recorder of a ride is the
Board when the ride started there, else the Phone; the Apple Watch writes the Health workout when it ran one, else the
Phone may (setting + permission); the LILYGO never records and never writes Health; FTP has one writer (`setFTP`).

## 4. Commands, acknowledgements, idempotency

- BikeComputer control: `CTRL_REQ` carries `reqId` and the ride id; `CTRL_RESP` returns status (ok / bad state / needs
  confirm / wrong ride). A repeated request with the same id is answered, not re-applied.
- LILYGO events: `(deviceId, seq)`; the phone keeps the highest acknowledged seq per device (`CyWatchSession.acked`,
  persisted) and re-acknowledges duplicates without re-applying them; cumulative `Ack` lets a watch that missed an ack
  stop resending.
- Apple Watch commands: the recorder's one-owner rules apply (`startMode`, `isActive`), so a repeated Start is a no-op.
- Ride steps (R-020): versioned per workout; the board rejects an older version and acknowledges with a status.

## 5. Offline queue and reconnection

- LILYGO: bounded `EventQueue` in firmware, resend on reconnect, explicit overflow warning (never silent loss); the phone
  reassembles frames split across notifications and resynchronises after a corrupt frame (`CyWatchSession.receive`).
- BikeComputer: ride history sync by `highestStoredRideId` per board; profile sync by monotonic version with ack.
- Phone: everything is stored locally first (`Store` JSON, atomic writes); Health export failure never loses the ride.

## 6. Adapters vs business logic

| Adapter (device-specific, no training logic) | Talks to | Business logic it must not contain |
|---|---|---|
| `DeviceLink` (BikeComputer BLE) | BCLink codecs | ride completion, FTP, plan |
| `WatchLink` (Apple Watch) | WatchConnectivity | ride ownership decisions (made by `RideRecorder` / `RideControlPlan`) |
| `CyWatchLink` + `CyWatchCoordinator` (LILYGO) | CyWatchWire / CyWatchSession | set logging rules (in `CyWatchEvents`, pure and tested) |
| `BLESensors` (direct sensors) | GATT decoders | source priority (in `SensorHub`) |
| `HealthMetricsReader`, `HealthImport`, `RideHealthExport` | HealthKit | precedence, dedup (pure `HealthPrecedence`, `SleepAggregation`, `RecoveryAnalysis`) |

The rule: a device adapter produces plain values with source + time; `SensorHub`, `RideRecorder`, `Store` decide.
UI never reads a device directly. Screens read `Store` / `SensorHub` / `RideRecorder` models.

## 7. Contract tests that detect breaking changes

- Byte vectors copied from or generated by the firmware for every message type (BCLinkTests, LinkV12Tests,
  CyWatchWireTests) — a codec change on one side fails the other side's test.
- Unknown-tag / truncated-frame / wrong-version behaviour tested (BCLinkTests, CyWatchSessionTests).
- Capability gating tested (RideStepsSyncTests: no shipped board reports 0x800 → nothing is sent).
- Ownership rules tested (FTPOwnershipTests, RideControlPlanTests, RideRecorderDisconnectTests, CyWatchSessionTests).
- Data integrity after relaunch and delete (DataIntegrityGapTests, RideChainTests).

## 8. Migration plan for an incompatible change (when one is unavoidable)

1. Add the new message/version beside the old one; both encoders and decoders live in the repo.
2. The app detects the device's version (INFO caps / protocol `ver`) and uses the newest both sides share.
3. Connections shows the device's version and, when below the minimum, "Firmware update available" with what changes —
   the app keeps working with the old contract.
4. Firmware flashing remains a separate owner approval; the old contract is retired only after the owner confirms
   every device is updated.
