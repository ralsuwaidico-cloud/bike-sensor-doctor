# BikeComputer diagnostic report transfer — iPhone side (Link 1.2.3)

Spec: `docs/LINK_V1_2_SPEC.md` § "1.2.3 — diagnostic report transfer" (firmware 0.7.3, cap `0x400 DIAG_XFER`).
The phone pulls; the board never pushes report data. Older firmware (no cap) never receives a request and the app shows
nothing for it.

## Engine rules

1. **Start**: 3 s after the link is Ready with cap 0x400 (connect-time traffic goes first), and on every `diag_ready`.
   A `diag_ready` during a transfer lists again when the current one ends.
2. **List**: `DIAG_LIST_REQ` → collect `DIAG_INFO` until `DIAG_LIST_END`.
3. **Queue**: reports with `state 0` (pending), oldest `report_id` first, that are not on this phone. Dedupe key =
   (board id from INFO tag 07, report_id). A report already saved here (or deleted here by the rider — a tombstone
   meta stays) is never pulled again; if the board still lists it as pending, the phone sends `DIAG_ACK` again with the
   stored crc. Reports with `state 1` that are not on this phone are not pulled.
4. **Pull**: `DIAG_CHUNK_REQ(report_id, offset, max_len)` one at a time, `max_len` from the link (see "Chunk size"). Each chunk is appended to
   `<id>.part` on disk immediately, so the resume point after a disconnect, a board restart or an app restart is the
   partial's length. A partial whose size/crc differ from the current DIAG_INFO is discarded (restart at 0).
   Late or duplicate chunks (offset ≠ expected) are ignored.
5. **Verify**: when `offset == size`, crc32 (IEEE) of the whole file. Match → move to `<id>.txt`, write meta, then
   `DIAG_ACK(report_id, crc)`. **The ACK is sent only after the crc matched.** The board's `DIAG_INFO state 1` reply marks
   the meta `boardAcknowledged`; if it is lost, the next list re-acknowledges.
6. **Mismatch** (also: more data than `size`, `last` before `size`, `DIAG_ERR 2`): delete the partial, restart from 0,
   up to 3 times; after that the report is left on the board for this app session (`lastError` explains).
7. **DIAG_ERR**: 1 unknown id → drop partial, next report · 2 bad offset → as 6 · 3 storage read error → same offset
   again after 2 s, up to 3 times, then keep the partial and move on (resumes next connection) · 4 busy (more than 4
   requests outstanding, or a ride recording on the board) → same request after 10 s, no limit · 5 link too small → stop,
   no retry, the report stays on the board · other codes → as 3. During listing: busy → list again after 10 s; others → after 2 s, 3 times.
8. **Timeouts**: 5 s per request, 3 retries of the SAME request (same offset, same size — the size never depends on
   timeouts; the 128-byte fallback of the first version was removed). After the 3rd retry the session pauses; the partial
   stays and the next connect / `diag_ready` resumes it.
9. **Rides** (LIVE has priority):
   - a ride recording on the **board** (its fresh LIVE says `ride_state` RUNNING): no chunk request at all; the engine
     looks again every 10 s (the board would answer BUSY anyway). LIST / ACK are single small writes and still allowed;
   - a ride recording on the **phone**: at most one `DIAG_CHUNK_REQ` per second (scheduled, not dropped);
   - otherwise back-to-back, one outstanding request; the board paces its replies (>= 200 ms apart, only when its LIVE
     frame has gone and its notify queue / mbufs have room).
10. **Disconnect**: `linkDown()` clears the in-memory session only.

## Chunk size (docs/LINK_V1_2_SPEC.md 1.2.3 — the same formula on both sides)

A DIAG_CHUNK is `25 + data` bytes: header 8 + `01` report_id 6 + `02` offset 6 + `03` data tag/len 2 + `04` last 3
(`BCLink.diagChunkOverhead`, checked against the encoder for 0…155 data bytes). One notification carries ATT_MTU − 3 bytes,
one Link message at most 180. The phone asks for

    max_len = min(180 − 25 = 155, (ATT_MTU − 3) − 25)      ATT_MTU − 3 = CBPeripheral.maximumWriteValueLength(for: .withoutResponse)

(`BCLink.diagRequestMaxLen`, `DeviceLink.maxNotifyBytes`; notifications use the same negotiated MTU). MTU 185 (iOS) → 155,
247 → 155, 517 → 155, 100 → 72; below MTU 29 nothing fits: the phone does not ask and says so. While the size is unknown
(not connected) it asks for 155 — harmless, because the board computes `min(max_len, 155, (its negotiated ATT_MTU − 3) − 25)`
from its own MTU event, so no notification can ever exceed the link, and a 0.7.3 board never sends the 185-byte chunk the
first draft allowed. The phone always continues at `offset + len` of the chunk it received.

## Storage

`Application Support/Diagnostics/<board-id>/` with the board id's `:` replaced by `-`:
`<report_id>.txt` (verified report), `<report_id>.json` (meta: size, crc, created, kind, summary, firmware, received,
acknowledged, seen, deletedByUser), `<report_id>.part` + `.part.json` while transferring. Default backup behaviour.
Nothing is deleted automatically. The rider deletes a report from the list (swipe) or the viewer; the text goes, the
meta stays as a tombstone so it is never downloaded again.

## UI

- Connections › BikeComputer and Connections › Diagnostics: section "BikeComputer diagnostic reports" — only when
  the board has the cap or reports are saved. While transferring: **Diagnostic report ready** + progress. After a
  save in this session: **Report saved** + "Kind · firmware · created · size" and the board's summary line. Link to
  the report list.
- Report list (newest first, "new" dot, swipe to delete) → full text viewer (monospaced, selectable) with **Share**
  (system share sheet with the `.txt` file — to Claude, mail, Files, …) and **Delete** (confirmation).
- Home: ONE banner "BikeComputer crashed earlier — report saved" while a crash report (kind 1) is unseen; opening it
  or the ✕ clears it. Nothing on the Ride screen.
- "Export diagnostic report" JSON: new `boardReports` list — id, kind, firmware, created, received, size, crc32,
  summary, acknowledged. Never the text, never the board address; the export is scrubbed as before.
- Upload: `DiagUploadHook` exists only as a hook — `ReleaseFlags.diagUploadEnabled = false` hides the consent toggle,
  consent defaults to off, and `upload` returns false without any network call in this build.

## Cross-tests with the firmware (resolved integrator notes)

1. The 160-byte / 185-byte size conflict is resolved by the formula above on both sides (firmware 0.7.3 final, this app).
2. `DiagFirmwareVectorTests` decodes the firmware's own bytes: the BLE_LINK_PROTOCOL.md vectors, and the generated fixture —
   DIAG_INFO / LIST_END / diag_ready metadata, every DIAG_CHUNK of a 7301-byte crash report built by the firmware's report
   builder at ATT MTU 23 / 100 / 185 / 247 / 517 (offsets, lengths, `≤ MTU − 3`, `25 + data`, reassembly, CRC-32), ACK
   replies (state 1 / state 0), duplicates, end-of-report, every DIAG_ERR code (1–5), INFO of 0.7.3 (cap 0x400) and 0.7.2
   (no cap). It also asserts that Cyclift's encoder produces the exact request bytes the firmware fixture contains, and
   replays the firmware's replies through `DiagTransfer` (full pull at each MTU, disconnect after 20 chunks + app restart →
   resume at 3100, duplicate chunk ignored, BUSY during a board ride, ERR 5 stops).
3. The reverse direction (Cyclift's request bytes into the firmware parser and server) is
   `firmware/waveshare/test/host/test_bc_diag.c` `test_ios_requests`.
4. Compatibility: firmware without cap 0x400 → `DiagReportCenter.transferAllowed` is false and no DIAG byte is sent;
   firmware with the cap + an older app → nothing asks, the board keeps every report (it never deletes an unsent one;
   `test_old_app_keeps_reports`). diag_ready is ignored by the older event decoders.
5. The phone accepts `diag_ready` on the Events characteristic **and** on Control.
6. Required fields: DIAG_INFO needs tags 01/02/03, DIAG_CHUNK 01/02/03, DIAG_ERR 02; otherwise the message is ignored.
   summary ≤ 40 B and firmware ≤ 16 B — longer values are skipped (not truncated).
7. The phone sends `DIAG_ACK` again for a report it already holds whenever a list shows it pending.
